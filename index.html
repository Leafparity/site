Equivalence proofs for tree models

Is your ONNX model the same model you trained?

Leafparity compares an XGBoost, LightGBM or scikit-learn tree model with its ONNX conversion over every possible input. It either proves the two always agree, or shows you exactly which inputs get a different answer.

The problem

Test sets rarely hit the difference. Production traffic does.

When a conversion goes wrong, it goes wrong in slivers of the input space one float step wide: around a threshold, at exactly zero, or only for missing values. Comparing predictions on held-out data almost never lands there.

  • Rounded thresholds

    A double threshold stored as float32 moves slightly. Inputs in the gap take a different branch.

  • Zero treated as missing

    LightGBM's missing_type=Zero is ignored by the converter, so an exact 0.0 goes the other way.

  • NaN routed differently

    scikit-learn decides per node where NaN goes. The converted model sends it the other way at some of those nodes.

What you get

A proof, or the exact inputs that break it.

Leafparity doesn't sample. It reproduces each runtime's arithmetic, including every cast, preprocessing step, comparison and missing-value rule, and walks both models together through every tree.

EQUIVALENT

Proof that the models agree on every input

For every possible input, both models reach corresponding leaves. Outputs can differ only by the stated floating-point rounding allowance.

exit code 0
NOT EQUIVALENT

Every disagreement, with a witness

Each place in each tree where the models differ, the exact set of affected inputs, and a concrete input you can run yourself. You also get the largest difference found and a proven upper bound.

exit code 1

If a model uses something Leafparity can't analyse exactly, it says so and stops (exit code 2). It never guesses. The exit codes let you use it as a CI step.

Trust

Every report checks its own work.

Three checks run on every analysis, in this order. The report shows the result of each one.

  1. 1

    Self-check before any analysis

    Inputs are built to reach every split node and sit exactly on its boundary and one float step either side, including zeros, tiny values and NaN. They run through the real libraries and through Leafparity's model. If a single decision differs, for example because a library update changed its arithmetic, Leafparity refuses to certify.

  2. 2

    Witness verification

    Every reported problem, and the worst case, comes with an input that has been run through both real runtimes. The report states whether the observed difference matches the prediction.

  3. 3

    Independent cross-check

    Thousands of boundary inputs run through both runtimes without using the analysis engine at all. Every observed difference must fall within the proven bound.

Working with us

Three steps from email to answer.

  1. STEP 1

    Send both models

    The original model file and the .onnx file, plus whether production feeds float32 or float64 values.

  2. STEP 2

    We run the check

    Within two business days you get the full report: the verdict, every problem found, a witness input for each, and the proven worst case.

  3. STEP 3

    Fix or certify

    If the models differ, the report shows where to fix the conversion. If they match, you have a record you can file with your model documentation.

About your model files

We see only the two files you send: the original model and its ONNX conversion. Never your training data, never your customers' data. Files are deleted once the report is sent; ask and we'll confirm it in writing. Prefer to keep everything in-house? Leafparity is open source and runs on your own machine.
